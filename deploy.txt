Solvn — static build

The contents of this folder are the site root of https://solvn.site. The
hosting repo mirrors this folder, so a deploy means: replace the repo's files
with these, commit, and push. That is the whole install — there is no server
code, no database and nothing to build.

What this copy does:
  - Search, browse, details pages, the player, watch history, favourites,
    settings and all 12 languages work as normal.
  - On solvn.site the central Supabase project is built in: accounts, profiles,
    card binders, packs and XP sync to the one Solvn database — once its tables
    exist. Until they do, the site quietly keeps everything in the browser that
    made it, which is why the leaderboard can look empty. The next section is the
    one paste that switches the real thing on.
  - A browser that has not signed into the central cloud keeps a local copy of
    everything (lib/device.js), so cards and messages still work between
    sign-ins; Settings ▸ Cloud sync carries that data up with one tap.
  - The bell asks AniList for air dates directly and compares them against this
    device's saved list, so episode notices work without any server.

ACCOUNTS, THE LEADERBOARD, THE VISITOR COUNTER — one thing to switch on.

Nothing in this folder is a server, so the central database is a Supabase project
the pages talk to directly. Its address is already compiled in (js/lib/cloud.js:31
— the public "publishable" key beside it is public by design; the tables answer
only what the SQL below allows). The project has no tables yet, which is the whole
reason sign-ups stay on one browser and the numbers on the admin desk are honest
but local. One paste fixes it:

  1. Open supabase.com and sign in with the account that owns that project.
     If you never made it, make one now: New project, any name, any region, then
     do step 3 and put the new Project URL and publishable key (Project Settings
     ▸ Data API) into js/lib/cloud.js:31, commit and push. That is the only edit
     the site needs.
  2. Inside the project: SQL Editor ▸ New query.
  3. Open docs/supabase.sql from this folder, select all of it, paste, press Run.
     It creates six tables, the functions every page calls and the rules that say
     who may read them. Running it twice is safe — it changes nothing the second
     time.
  4. Authentication ▸ Providers ▸ Email: however you leave "Confirm email", the
     signup works. With confirmation on, the member confirms and the profile row
     is made for them automatically by the trigger in that file.
  5. Prove it: open https://solvn.site in a private window, sign up once, then
     look at the leaderboard in your normal window. The new name is there. If the
     admin desk says the database is not set up, step 3 did not run.

Your own admin access: the locked functions in that file answer one address,
fakelokman36@gmail.com, and any row you mark is_staff = true by hand in the Table
Editor. Sign in on solvn.site with that address. If the desk says "Please sign in
as the owner", the browser holds a local session, not a database one — open the
admin desk and use the Central cloud panel's Connect button, which signs that
browser into Supabase itself.

What the counter counts, and what it deliberately does not:
  - Page views: the address of the page and the moment. No name, no e-mail, no
    IP, no country, nothing that points back at a person. A visitor does not
    need an account to be counted, and nobody learns that a specific person was
    on a page.
  - Who is signed in right now: handle, the page they are on, and the time.
    Members only — an anonymous visitor never appears in that list.
  - Both are readable by you alone, in the admin desk. The database refuses the
    same question from anybody else, including a signed-in member.
  - No location of any kind is stored or displayed, for anybody — including you.
  - One honest trade: a page view has to be writable by a visitor who has no
    account, so that one insert is open to the internet. It writes a route and a
    moment and nothing else, the desk keeps 90 days of it, and nobody — not even
    you — can read or change anything else through it. Someone determined to be
    annoying can inflate the totals; they cannot see or touch a member's data.

MOVIES & SERIES — what works today, and what a server would add.

The anime half runs on AniList, which answers browsers directly. The film half
reads TMDB, and a TMDB key cannot be put inside a page: whoever opens DevTools
would own it. So film calls go to a /tmdb endpoint that runs beside the site,
and three sibling routes do the rest: /ia (public-domain copies), /health (which
embed host answers this title) and /stream (the direct-file resolver).

GitHub Pages — what www.solvn.site points at today — runs no server code, so all
four answer 404 there. That no longer means empty pages: this folder carries
data/catalogue.json, a dated snapshot of the nine film and series shelves
(trending, popular, top rated, now playing, upcoming, airing today, on the air —
for both movies and TV), with posters, synopses, cast, trailers and the first
two seasons of every series in it. The pages read that file when no proxy
answers, so browsing, search, detail pages, watchlists, continue-watching and
trailer playback all work on the live site with no server and no key. The film
hub says "Offline catalogue · 138 titles · dated <day>" on top so nobody mistakes
a snapshot for the whole database.

Two things a snapshot cannot do, and what to do about them:

  - Search covers the ~140 titles in the file, not all of TMDB, and the shelves
    only move when the file is rebuilt. Rebuild it on any machine that holds the
    key: with serve-solvn.mjs running, `node build-catalogue.mjs` in the folder
    above the site, then commit data/catalogue.json. Or deploy the proxy below,
    which reads TMDB live and drops the snapshot entirely.
  - The direct-file engine and the embed health pre-flight need /stream and
    /health. Without them the watch page hands over to the embed pool, which
    builds its addresses from the TMDB id in this file and so still plays; the
    clean room asks Archive.org directly and works here too, because Archive
    answers browsers itself.

To put a live TMDB behind the site, deploy the same folder on Netlify
(netlify.toml and netlify/functions/proxy.mjs in this repo are the whole server):

  1. app.netlify.com ▸ Add new site ▸ Import an existing project ▸ GitHub ▸
     pick lokmanfree100-wq/solvnsite. Build command: leave empty. Publish
     directory: leave as the repository root.
  2. Site configuration ▸ Environment variables ▸ Add another variable:
     TMDB_API_KEY = the v3 key from your TMDB account, tick "Secret".
     (This is the same value the dev server reads from tmdb.key. It never goes
     into this repo, and the function refuses to answer without it.)
  3. Site details ▸ Domain management ▸ Add a domain ▸ www.solvn.site. Netlify
     then shows one CNAME target. At Namecheap ▸ Advanced DNS, edit the existing
     www CNAME (it points at <repo>.github.io now) to that Netlify target, and
     delete the CNAME file from this repo once the certificate is issued.
  4. One line of code so every visitor uses that host, not only yours: open
     js/lib/proxy.js and set
       export const API_HOST = 'https://<the-name>.netlify.app';
     commit and push. Leave it as '' if the routes are same-origin instead.

Steps 1-3 are account buttons; nobody can click them for you, and nothing here
changes the live site until they are. The alternative, if you would rather keep
Pages: run serve-solvn.mjs on any small server you own, at the same address the
site is served from — that answers all four routes without step 4.

ANIME PLAYS ONLY WHAT YOU CHOOSE — and right now you have chosen nothing, so the
player says "No video source is configured yet."

Solvn hosts no video. Settings ▸ Streaming servers stores what plays, and that
store lives in one browser: configuring your laptop configures your laptop, not
the site. For everyone, name the sources once in the repo — js/lib/defaults.js,
an array of entries in this shape:

  { name: 'My player', url: 'https://player.example/anime/{anilist}/{episode}?audio={audio}', tracks: ['sub', 'dub'] }
  { name: 'My CDN', url: 'https://cdn.example/{anilist}/ep-{episode}.m3u8', tracks: ['sub'] }

A file address (.m3u8/.mp4/.webm) plays in Solvn's own player with no third-party
page on the screen at all, so it carries no ads — that is the shape to prefer. An
embed page is framed and sandboxed so it cannot move your visitors elsewhere, but
whatever that page draws inside its own frame, including its advertising, belongs
to it and Solvn cannot filter it from outside. That is why this list ships empty
and why AniGato is blocked in code: the choice of host is the choice of what your
visitors see, and nobody should make it for you. Entries here pass the same gate
as a typed one — https only, placeholders checked, blocked hosts refused — and
appear in Settings as a locked "Site default" row.

After uploading, open the site once and press Ctrl+F5 so the old copies held in
your browser are replaced by these files.
